# Synthetic consumer packet proposal (CP-12.01)

This is bounded offline preparation for [#58](https://github.com/Pick-Your-AI/pick-your-ai-catalog-pipeline/issues/58), not an accepted consumer interface, adoption service or runtime. Required accepted outcomes from #9 (CP-02.02) and #48 (CP-10.01) remain blocked; receiving acceptance and independent review are absent. Keep #58 open. Pipeline completion, website adoption, Apple adoption, Android adoption and installed-runtime evidence are separate decisions.

## Draft contract and exact inputs

The additive proposal is `schemas/v0.1/consumer-receipt.schema.json`, deliberately versioned alongside the existing `catalog-pipeline-draft-0.1.0` contracts rather than the issue's proposed unversioned `schemas/consumer-receipt.schema.json`. This preserves the draft namespace; it neither alters frozen builder v1 nor establishes a new accepted interface. Schema/semantic compatibility and receiving-owner review remain required.

`examples/synthetic/consumer-packet.json` pins the actual `examples/synthetic-release.json` bytes, manifest ID/revision, and all three actual artifact paths, record IDs/revisions and SHA256 digests. Its source fixture baseline is repository commit `77f92e8ee6b4c35a7cacb3be6ef26462888188a7`; artifact source revisions and observed dates remain in the unchanged catalog fixtures. Regenerating whitespace changes byte identity. No fixture hash proves rights, source truth, reviewer identity or authentic provenance.

`src.consumer_handoffs.packets.check_packet(packet_bytes, manifest_bytes, artifacts, *, consumer)` takes bytes and an explicit plain dictionary of artifact path to bytes. It returns the declared `unresolved`, `rejected` or `rehearsal` status only after consistency checks. The committed packet is `unresolved`; all receiving acceptance remains `unknown` with a reason. Generated code, a schema pass or a hash match cannot supply acceptance. Adoption/production-ready status, actual receiving identities, signatures and permission claims have no supported packet fields.

Only fixed repository-owned schemas are read at module import. The checking function performs no filesystem/network I/O and never follows packet paths, source URLs or embedded instructions. It checks the receipt, manifest and record draft schemas; exact consumer/version; manifest identity/revision/raw-byte hash; and exact artifact sets, identity/revision/raw-byte hashes and synthetic markers. Missing, extra or duplicate paths/record IDs are rejected. An internally consistent caller-supplied manifest is still untrusted: authentic release provenance requires a separately accepted trust boundary.

## Bounds and rejection behavior

Packet and manifest each allow at most 131072 bytes; artifacts at most 32 entries, 262144 bytes each and 2097152 bytes in aggregate. JSON permits at most 32 nested containers, 10000 visited values/keys and 8192 characters per string. Receipt lists allow 1–32 unique entries and bounded text. The current manifest path grammar is restricted to canonical `examples/[a-z0-9-]+.json` names; paths are identifiers only. Absolute paths, traversal, backslashes, encoded paths and URL locators cannot be artifact keys.

Strict UTF-8 decoding rejects malformed JSON, duplicate keys, nonfinite/fractional/exponent JSON numbers, lone surrogates and unsupported fields. Decimal quantities use exact strings under the draft contract; revisions use exact positive integers without imposing a new 32-bit cap. Encoded-byte and structural bounds still limit each input. Canonical IDs require the actual end of the string, so trailing controls cannot be mistaken for a valid URN. Fixed `PacketError` diagnostics contain no input-derived text, and parser failures discard parser-owned causes and contexts. They do not scrub traceback locals, caller-owned exception context, argument capture or telemetry. Malformed/inconsistent input raises that error; a well-formed synthetic rejection receipt returns `rejected` without approving any use.

The packet boundary applies complete-string checks to manifest and record IDs, artifact record references, rights decision references, claim IDs, source/material IDs, optional evidence receipts and relationship targets. It preserves the existing `urn:pya:[a-z0-9][a-z0-9:._-]+` grammar for these fields; nested references do not gain a new synthetic-only namespace restriction. Claim paths likewise retain `[a-z][a-z0-9_.-]+` with a required actual end. The receipt schema already requires complete synthetic packet and anchor IDs. Manifest approval references are also checked, while synthetic manifests still forbid any approvals. Invalid tokens are rejected without trimming or normalization. Free-form claim values, source revision assertions, evidence basis, conditions and scope prose retain their existing rules. These are receiving-boundary checks; the legacy manifest/catalog schemas, source fixtures and frozen builder v1 remain unchanged.

## Separate receiving scopes

The packet records proposed versions, mapping limits, notices, precision constraints, unsupported fields, receiving criteria and explicitly unknown acceptance for **each** consumer. These declarations describe review requirements; this checker does not execute the consumer tests or decide their substantive adequacy.

| Scope | Canonical receiving authority and required evidence |
| --- | --- |
| Website | Reconcile existing website #15–#18, [data integration](https://github.com/Pick-Your-AI/pick-your-ai-website/blob/main/docs/DATA_INTEGRATION.md) and frozen adoption. Receive the exact snapshot/pricebook/ruleset/dependency-graph/build-lock tuple. Test unknown/current-state disclosures, restricted display/export, correction, withdrawal and rollback. A newer snapshot does not expire saved builds. |
| Apple | Reconcile Apple #23, [repository scope](https://github.com/Pick-Your-AI/pick-your-ai-apple/blob/main/docs/REPOSITORY_SCOPE.md), scoped research receiving decision and exact conformance contract-lock bytes. Run app-owned exact-version receiving, incompatible-release rejection, update/correction, cache/offline and withdrawal tests. |
| Android | Reconcile Android #35, [revision handoff](https://github.com/Pick-Your-AI/pick-your-ai-android/blob/main/docs/CONTRACT_REVISION_HANDOFF.md) and [service baseline](https://github.com/Pick-Your-AI/pick-your-ai-android/blob/main/docs/SERVICE_BASELINE.md). Run Android-owned hash/version, unknown-capability, stale-cache, rights-change and rollback tests. |

Read activation, saved builds, evaluate/estimate and authorization stay in website `services/planner-api`. This proposal supplies no backend or client implementation. Frozen OpenAPI reads retain global bearer authentication; anonymous publication would require a separately accepted boundary. Public display and redistribution need separate source/material/use decisions and notices; current GPUs.io exclusion remains in force. No rights decisions are created by this packet.

Preserve field attribution, exact decimal strings, units, currencies, regions, operating conditions, effective/access dates, source revisions and unknown reasons. Broad catalog kinds have no automatic builder v1 mapping. Unsupported fields/endpoints stay explicit, including current-catalog/resource-estimate gaps. One consumer's future receipt cannot accept another consumer or broader use.

## Evidence and next acceptance

The registered example validator checks both schema and packet consistency. Tests exercise the current fixture repeatedly without I/O, independently changed manifest/record identities, revisions, versions and bytes, duplicate/missing/extra entries, unsafe paths, false adoption claims, malformed/over-limit input and schema-valid semantic mismatch through example-validator integration. Nested identifier and claim-path negatives recompute artifact and manifest digests so stale hashes cannot mask rejection; neighboring valid identifiers and free-form text remain accepted. These are local synthetic checks, not client execution, live source checks, cryptographic authentication, production readiness or rights clearance.

Further acceptance needs accepted #9/#48 outcomes, affected producer/contract/consumer reviews, real exact-revision receiving decisions with notices and supported mappings, independent latest-push review, and separately authorized runtime/deployment evidence. No owners, acceptance receipts or operating permission are inferred. Withdrawal or migration of this additive draft requires explicit packet/schema version handling; removing the proposal restores the prior synthetic-only baseline without changing existing manifest or frozen v1 bytes.
